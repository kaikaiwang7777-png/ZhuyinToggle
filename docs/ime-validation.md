# 微軟注音輸出測試（尚未驗收）

## 核心整合開發版

目前分支的開發版已將 REG_SZ 讀取、切換、回讀及登錄通知整合至 `ImeModeService`，系統匣、快捷鍵、設定按鈕共用同一服務。開發版實機測試時觀察到產品設定顯示簡體而記事本曾輸出繁體；使用者回報第一次快捷鍵成功、第二次失敗。測試過程曾有使用者與自動化交錯操作，原因尚未定位，不能據此判斷是哪一層錯誤。由於實際輸出無法可靠查詢，修正後圖示一律顯示灰色未知；工具列文字與設定視窗分別標示登錄設定值及實際輸出未知。讀取、寫入或回讀失敗會顯示未知及錯誤。以下歷史測試中的「產品切換停用」敘述只適用當時版本。

後續在使用者暫停操作的受控測試中，先以 Windows 原生設定頁建立繁體輸出基準，記事本輸入「電腦」；一次產品快捷鍵後，產品設定視窗顯示「簡體」，但記事本仍輸出「電腦」。第二次快捷鍵後，無法可靠確認設定視窗無障礙資訊是否即時更新，故不判定第二次的設定結果。最後以原生設定頁切換後還原繁體，並在記事本確認輸出「電腦」。此結果證明本次產品設定顯示與實際輸出不一致，尚不足以判斷內部原因。

| 正式程式開發版驗收 | 狀態 |
|---|---|
| 記事本繁簡往返連續十次 | FAIL（尚未完成連續驗證；曾觀察到設定與輸出不一致，使用者回報第二次切換失敗） |
| Chrome 輸入與前景快捷鍵 | NOT TESTED |
| 系統匣左鍵、圖示與外部設定同步 | NOT TESTED |
| 快捷鍵設定重啟保存、登入自動啟動 | NOT TESTED |
| 正常退出、一般使用者權限 | NOT TESTED（新版尚未驗證） |

登錄服務的模擬單元測試不能取代上述實機驗收。

## 可選診斷與 A/B 待測

以 `--diagnostics` 啟動開發版才會在目前使用者的 `%LOCALAPPDATA%\ZhuyinToggle\diagnostics` 寫 JSONL，含 SID 等私人資料，絕不放入公開倉庫。紀錄 WM_HOTKEY ID、執行與節流、值及 REG_SZ 類型、目標、寫入回傳、立即與約 500/1000/3000 毫秒讀值、登錄通知和程序環境。延遲時間會記錄實際取樣時間；取樣非原子，關閉程序前的未完成取樣可能遺失。每筆值偏離目標不表示一定遭其他程序覆寫：其他使用者操作、下一次切換與監看競態均可能造成變化，寫入者須由 ProcMon 證據佐證。

## P0 受控對照紀錄

測試由同一互動使用者於 session 1 啟動；去識別化比較顯示產品與原型 SID 相同、皆為 x64，父程序為 Explorer，使用 64 位元程序的預設登錄檢視。記事本使用原有注音鍵位，每個詞語提交後才下一次切換；測試前後均以「電腦」確認繁體。實際作用中的 TSF 設定檔尚未以系統 API 獨立識別，此限制仍存在。

| 方式 | 操作及診斷 | 記事本觀察 |
|---|---|---|
| B 產品，記事本持續前景 | 兩次 WM_HOTKEY ID 1 都進入切換，未遭 250ms 節流；分別成功寫 REG_SZ 0→1、1→0；立即及約 500/1000/3000ms 回讀均為目標值，監聽器收到通知 | 第一次寫 1 後約 0.11 秒開始組字及約 19 秒後再次組字仍為「電腦」 |
| A 原型，有 MessageBox | 0→1 寫入及各次取樣均為 1；訊息視窗保留，另回到記事本 | 寫入約 10 秒後輸出「电脑」；再由原型寫 0，輸出「電腦」 |
| A 原型，無 MessageBox | 由 Windows 執行對話框啟動原型，過程仍發生焦點切換；診斷模式僅延長程序生命以記錄 3 秒取樣，不是產品修復 | 分別寫入 1、0 後觀察到「电脑」、「電腦」 |
| B 產品，額外前景切換 | 熱鍵寫入 0／1；切離記事本到既有原型視窗後再回到記事本 | 曾觀察到原本未同步的輸出轉為與設定一致；再以 0→1 重做一次亦觀察到轉為「电脑」 |
| C 原生設定頁 | 設定頁選擇簡體、再選繁體；自然發生視窗焦點變化 | 依序觀察到「电脑」、「電腦」 |

此次取樣點未見目標值偏離，但取樣間隙與其他程序寫入者無法由此日誌排除；監聽器不提供寫入者身分。焦點切離／返回與輸出更新有相關性，是候選線索，不是已證明的內部根因或可安全重現的公開通知介面；首次焦點對照曾使用 Shift，因此還有其他干擾因素。訊息視窗不是本次在執行對話框啟動原型後輸出改變的必要條件，但啟動對話框本身已改變焦點，不能單獨排除其他差異。沒有把強制切焦點、廣播訊息或等待當成修復。

該產品診斷工作階段共記錄 6 次 WM_HOTKEY、6 次進入切換、0 次被節流、6 次寫入回傳成功；延遲回讀樣本未見偏離，收到 12 次登錄變更通知（包含測試期間原型和設定頁的操作，不能把通知數當成產品切換次數）。測試結束時使用者從系統匣結束診斷版，確認產品程序數為 0，記事本確認恢復繁體。

[Microsoft TSF Thread Manager 文件](https://learn.microsoft.com/en-us/windows/win32/tsf/thread-manager)說明 TSF 處理文件與輸入焦點關係，並提供事件通知；這僅支持進一步調查焦點事件，不代表該 API 已被證明可以跨程序重新載入微軟注音設定。

本次 GUI 自動化未能精確安排每個方案在寫入後恰好 0、500、1000、3000 毫秒啟動組字；這些輸出時序矩陣仍是 **NOT TESTED**，只有登錄值取樣完成。未完成連續十次產品測試、Chrome 與輸出狀態偵測；不發布正式版本。

前次測試曾切換 Windows 輸入法，未確認作用中的設定檔；不能據此推論微軟注音機制不可行。本次沒有操作語言切換，以同一個既有記事本及標準注音按鍵輸入測試。Windows 設定頁的「繁體中文（台灣）」選項顯示已安裝「微軟注音」，輸入時亦出現注音組字與候選字；但尚未透過 TSF 獨立確認記事本當下作用中設定檔，仍有身分限制。PowerShell 與記事本均為同一使用者、同一互動工作階段。

| 方式 | 修改前 → 修改後的指定登錄值 | 實際輸出 | 重新選取或重載輸入法 | 結果 |
|---|---|---|---|---|
| 原生微軟注音常規頁，繁體 | REG_SZ 0x00000000 | 中國、電腦、學習 | 無 | 繁體輸出觀察成功 |
| 原生頁選簡體 | REG_SZ 0x00000000 → 0x00000000（命令執行環境讀值；與後續 ProcMon 記錄不一致） | 中国、电脑、学习 | 無 | 既有記事本立即輸出簡體 |
| 原生頁恢復繁體 | REG_SZ 0x00000000 | 後續 PowerShell 測試前由設定頁恢復 | 無 | 設定頁顯示繁體 |
| PowerShell Set-ItemProperty -Type String | 0x00000000 → 0x00000001（回讀為 String） | 中國、電腦、學習 | 無 | 本次未立即轉為簡體 |
| .NET RegistryKey.SetValue | 0x00000000 → 0x00000001（回讀為 String） | 中國、電腦、學習 | 無 | 本次未立即轉為簡體 |

兩次直接寫入皆已恢復 REG_SZ 0x00000000。原生頁選簡體時指定登錄值並未改變，表示不能假定此值反映實際輸出狀態；原因尚未確定。使用者回報先前的 PowerShell 操作曾成功；不得以這次觀察否定使用者的結果。

## 後續重現與儲存位置調查

**更正：先前「原生設定頁未寫入指定值」的推論不正確。** 下列快照僅描述命令執行環境的讀值，不能當成設定程序沒有寫入的證據。經使用者正常授權的 ProcMon 追蹤確認，`SystemSettings.exe` 在繁→简→繁操作期間，兩次成功對 `HKCU\Software\Microsoft\IME\15.0\IMETC\Enable Simplified Chinese Output` 執行 `RegSetValue`，資料分別為 `REG_SZ 0x00000001`、`REG_SZ 0x00000000`。同一波設定作業還寫入多個其他 IME／CPSS 值；可見 `ctfmon.exe` 查詢該值，但這些事件本身不證明哪個事件導致輸入法即時更新，也不能證明沒有未觀察到的 IPC 或通知。

此次擷取約 67 秒、約 373 萬事件；全量 CSV 僅留在本機私人工作區，未提交公開倉庫。未依據程序出現與否推斷完整的內部呼叫。先前命令工具讀值與設定程序在簡體期間的觀察不一致，其具體隔離或登錄檢視原因尚未確定。

將使用者提供的 `reg add` 命令改從 Windows 桌面「執行」對話框啟動後，在既有記事本觀察到簡體「国、电脑」，再執行還原命令後觀察到「中國、電腦」。與先前命令執行環境不同，這次互動桌面執行產生實際輸出變化；不能僅憑現象斷言原因是某一種隔離機制。

獨立 C# 原型 `tools/RegistryToggleProbe` 從同一互動桌面啟動，檢查既有值為 REG_SZ 且格式合法後，分別寫入並回讀 `0→1→0`；既有記事本透過注音組字依序顯示「中国、电脑」及「中國、電腦」。這是目前一台電腦、一次往返的可重現候選方法，不代表所有應用、使用者工作階段或 Windows 版本均可靠，也不代表可以只靠回讀設定來確認實際輸出；正式程式切換功能仍停用。

- 使用者後來提供的指令是 `reg add` 指定同一機碼、`REG_SZ`、資料 `0x00000001` 或 `0x00000000`；當時的實際輸出證據沒有保存。本次另以該 `reg add` 命令寫入 `0x00000001`，命令成功且 `reg query` 讀回 `REG_SZ 0x00000001`，同一記事本仍輸出「中國、電腦」；隨後以 `reg add` 還原 `0x00000000` 並讀回。此結果僅適用本次環境與操作條件。
- 本次系統登錄所報版本為 DisplayVersion `26H2`、build `26300.9818`；「使用以前版本的微軟注音輸入法」顯示關閉，測試時未更動。相同記事本中，原生頁選繁體後觀察到「中國、電腦」，選簡體後觀察到「中国、电脑」，選回繁體後觀察到「中國」。未重新選取輸入法；作用中 TSF 設定檔仍未獨立驗證。
- 對當前使用者 `Software\Microsoft\IME`、`Software\Microsoft\InputMethod` 和 `Software\Microsoft\CTF` 做切換前後快照：未辨識到可歸因於繁簡設定的變更；CTF 有組字計數變動。指定值在簡體期間仍讀為 `REG_SZ 0x00000000`。所檢查的 `Software\Microsoft\Windows\CurrentVersion\AppModel\SystemAppData` 鍵不存在或無法查詢，不能據此說該位置沒有變更。此比較不是完整系統追蹤，也不排除其他登錄位置、檔案、快取或 IPC。
- 可見同一工作階段存在 `SystemSettings`、`ctfmon` 與 `TextInputHost`；ProcMon 已確認設定值由 `SystemSettings` 寫入，尚未確認即時變更通知機制。絕不提交原始追蹤或私人資料。
- [Microsoft TSF 文件](https://learn.microsoft.com/en-us/windows/win32/tsf/predefined-compartments)說明轉換模式 compartment 屬於特定 thread manager；這不是它控制本設定或跨程序可安全修改的證據。C# 寫入已有單機往返觀察，但可靠的通知方式與私有介面相容性尚無從評估。

## UI Automation 唯讀概念驗證

Windows 26H2 build 26300.9818、簡體中文介面上，已在現有微軟注音設定視窗中觀察到輸出類型 ComboBox 的 AutomationId 為 `SystemSettings_Language_CHTBopomofoIME_OutputLanguage_ComboBox`。獨立 C# 原型 `tools/UiAutomationProbe` 可在指定已知視窗控制代碼後，要求唯一符合的 ComboBox、讀取 SelectionPattern，並在本次讀到「繁体中文」。這是設定頁的顯示選項，不是已獨立驗證的實際輸出狀態。

本次唯讀操作前後前景視窗相同。原型不啟動視窗；預設唯讀，另有必須明確指定的 `--set` 候選操作，僅使用 UI Automation 選取模式。在此版本及簡體中文介面上，選擇簡體與還原繁體後，記事本分別觀察到「中国、电脑」及「中國、電腦」；但兩次操作前後前景視窗均不同，存在焦點干擾。不同 Windows 版本和語言、異常失敗後的狀態還原均為 NOT TESTED。未辨識到唯一目標、選取模式不可用或文字不在已知清單時停止。不可根據單次結果宣稱 UIA 切換可靠，更不可將畫面座標作正式方案。

瀏覽器輸入、前景視窗 TSF 設定檔識別、實際通知機制與不同 Windows 版本相容性尚未測試。不得把登錄讀寫成功視為輸出切換成功。未完成實際驗收前不得發布 v0.1.0。

## 獨立功能測試

`tools/HotkeySmoke` 在同一 Windows 互動工作階段以獨立隱藏視窗註冊 `Win+Alt+C` 與 `Ctrl+Shift+F11`，分別收到 `WM_HOTKEY`；第二次註冊同一組合被拒絕，錯誤碼 1409；程式結束時執行 UnregisterHotKey。這是獨立測試程式的觀察，不等於產品的快捷鍵錄製、衝突提示、重啟保存或結束釋放均已實機驗收。圖示在 16、20、32 像素做了尺寸與背景色自動檢查，小尺寸視覺清晰度與系統匣動態切換仍未實機驗收。

使用者啟動 self-contained 開發版後，在記事本按 `Win+Alt+C` 顯示「切換功能尚未驗證，暫不可用」，確認產品的預設快捷鍵可觸發且未虛報切換成功。再次啟動同一執行檔，出現「ZhuyinToggle 已在執行」；關閉提示後檢查，互動工作階段只剩一個產品程序。這兩項是本次單機觀察，不代表設定錄製、開機登入或結束資源釋放已通過。

接續使用者從系統匣開啟設定介面，介面標示實際輸出無法確認。實機錄製並儲存 `Ctrl+Shift+F11` 後，從記事本觸發並收到未驗證提示。再錄製 `Win+Alt+C`，在儲存前讓獨立測試程序占用該組合；產品顯示 Windows 錯誤碼 1409，且原有 `Ctrl+Shift+F11` 仍可觸發。測試程序解除占用後，已將產品快捷鍵還原為 `Win+Alt+C` 並收到儲存成功回報。此測試未驗證重啟後設定保存；自動啟動曾操作開關，但未完成登入驗證或獨立確認實際登錄狀態。

使用者從系統匣選擇正常結束後，確認產品程序數量為 0；獨立測試程序隨即成功重新註冊 `Win+Alt+C`，並從記事本收到該組合的 `WM_HOTKEY`。這確認了本次正常退出後預設快捷鍵可重新取得；不能據此推論所有 GDI／視窗資源或非正常終止路徑均已驗證。

## 焦點對照（單機、探索性）

同一個互動工作階段與記事本，使用實體注音鍵位組字；每組由原生設定頁選簡體再選繁體，並在記事本確認「電腦」作為基準。使用唯讀 `GetForegroundWindow`、`GetWindowThreadProcessId`、`GetGUIThreadInfo` 及 `GetKeyboardLayout` 以約 50 ms 取樣；取樣可能漏掉短暫事件，HKL 不足以證明 Microsoft Bopomofo 身分。本輪未獨立取得記事本 TSF 作用中設定檔，因此身分仍有驗證限制。

- A：記事本前景及輸入焦點取樣保持不變，產品快捷鍵寫入簡體；實際為「電腦」「中國」。這次並非即時生效。
- B：另由繁體基準寫入簡體，切至檔案總管再回到記事本，前景視窗確有變化；實際為「电脑」「中国」。這是一次觀察，並不證明前景切換為必要條件。
- C：另由繁體基準寫入簡體，Ctrl+F 開啟記事本搜尋框，之後關閉並回編輯區；取樣中前景視窗始終為同一記事本，而焦點 HWND 由編輯區切到搜尋框再返回。搜尋框中曾組字輸入「电脑」「中国」，回編輯區後亦得到「电脑」「中国」。由於搜尋框曾接收組字，不能排除該額外操作的作用；此單次結果不證明僅改焦點就足夠，也不證明 TSF 內部機制。

## 簡化宿主：自動辨識與焦點對照先導實測

本次以獨立 WinForms 宿主、同一 Windows 互動桌面、同一輸入框為對象；以實際注音鍵位事件與 Enter 提交「電腦中國／电脑中国」，沒有貼上或注入完成的中文字。宿主自身 `GetActiveProfile` 回報 Microsoft Bopomofo 的 zh-TW 語言、CLSID 與 profile GUID（對照 [Microsoft 預設輸入設定檔](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/default-input-locales-for-windows-language-packs)），各樣本觀察到兩次 IME 組字開始／結束／結果事件。IMM 和視窗事件不能證明所有私有 TSF 狀態，判斷只限本宿主及本機。

- A 先導：繁體基準為「電腦中國」；寫入簡體後不改焦點，實際仍為「電腦中國」，繁→簡 FAIL。回寫繁體仍輸出「電腦中國」，但前次未真正進入簡體，因此簡→繁是 NOT TESTED，不能當作有效回程。之後另一次重複 A 得到相同現象。
- B 先導：基準「電腦中國」，焦點 A Leave → Button Enter → Button Leave → A Enter；輸出「电脑中国」。回寫繁體並相同焦點往返，輸出「電腦中國」；兩端各一次 PASS，完整往返 1/1，樣本僅一次。
- C 先導：基準「電腦中國」，焦點 A Leave → B Enter → B Leave → A Enter；輸出「电脑中国」。回寫繁體並相同焦點往返，輸出「電腦中國」；兩端各一次 PASS，完整往返 1/1，樣本僅一次。

B／C 每次返回 A 時，原游標／選取 `(4,0)` 曾變為全選 `(0,4)`；實驗版在自身欄位、沒有新的輸入且文字不變時，主動還原為 `(4,0)`，之後比較文字與選取相符。這是實際副作用，不可宣稱焦點往返全程不干擾。閃爍與組字中斷沒有獨立自動化驗證。設定最終回讀為測試前原始繁體值；未以登錄回讀代替輸出驗證。

各組五次往返尚未完成。先導樣本支持「在此 WinForms 宿主中焦點往返可能使設定被採用」的假說，但不能證明是唯一因素或正式可靠機制。B／C 的第二階段、不同應用、用戶操作競態及跨版本均未驗證。未將跨程序焦點操作或此實驗整合正式產品。

### 跨程序關卡

[Windows SetFocus](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setfocus) 的目標受呼叫執行緒輸入佇列限制；文件亦描述 `AttachThreadInput`，但這不等於已證明能無損、安全地操作其他程式。程式不使用該方法。[TSF Thread Manager](https://learn.microsoft.com/en-us/windows/win32/tsf/thread-manager) 管理文件與焦點；沒有找到文件支持從獨立工具呼叫自身 manager 即可要求第三方程式重新載入此微軟注音設定。IMM 的一般 context 關聯也不是此設定重新載入的證據。

Chromium 的 [多程序架構](https://www.chromium.org/developers/design-documents/multi-process-architecture/)分離瀏覽器與網頁 renderer；不能假設網頁文字欄位等同此 WinForms 控制項。記事本與 Chrome 的跨程序焦點、組字、游標及繼續輸入競態尚無可靠、安全、非侵入式路線，也未實機驗證。本輪不注入、不強迫切換前景、不模擬 Alt+Tab、不猜測性廣播；正式整合條件尚未達成。

## 同輪桌面與背景原始 reg query 對照

唯讀稽核目前 `RegistryImeStore.Read`：完整路徑為 `HKCU\SOFTWARE\Microsoft\IME\15.0\IMETC`，值名 `Enable Simplified Chinese Output`；先檢查存在與 REG_SZ，僅明確字串 0／1 映射繁／簡，其他情況丟出例外，`Refresh` 將可處理讀取錯誤標為 Unknown，並非解析錯誤一律回傳 0。先前背景直接讀取是該輪的即時 `RegistryKey.GetValue`，不是本次雙來源腳本；此稽核不能證明所有歷史觀察程式均無誤。

本次使用同一份唯讀腳本（本機檔案 SHA256 `EFC915BB56151A1054012807460FF99C8CBED15AE1609DEE71C22325D60E09D6`），分別由桌面「執行」與背景啟動；每筆呼叫 `C:\Windows\System32\reg.exe query`，分開保留 stdout、stderr、退出碼、PID、UTC、QPC 與唯一輪次，原始記錄僅在私人本機。兩個查詢程序記錄的 SID 相同、Session 均 1、均為 64 位元，reg.exe 的路徑與版本字串相同。桌面腳本記錄了 SHA256；背景腳本該欄為空，因此雖然兩次均指向同一路徑，**未獨立核實背景執行時檔案雜湊**；不能以路徑或 SID 相同證明同一實體登錄檢視。

原始繁體基準 REG_SZ 為 0，專用宿主以注音組字得到「電腦中國」及 TSF 設定檔／IME 事件。透過桌面「執行」提交未包裝的原始 reg add 簡體命令；在同一輸出簡體期間、還原前，選取同一 QPC 時間窗的各 7 筆成功 query：桌面 stdout 7/7 為 `REG_SZ 0x00000001`，背景 stdout 7/7 為 `REG_SZ 0x00000000`，退出碼均 0、stderr 均空。宿主以實際注音輸出「电脑中国」，IME 開始／結果／結束有記錄；在判讀完成後才經桌面「執行」提交原始繁體還原命令，兩來源之後均讀到 REG_SZ 0，宿主實際輸出「電腦中國」。這些 query 是獨立程序、離散取樣，不與寫入原子化，寫入命令退出碼未取得。
