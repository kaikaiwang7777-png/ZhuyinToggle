# 原生輸入設定更新：呼叫堆疊與 ETW 可行性

## 證據範圍

專案原始擷取位置保存 `ime-capture.CSV`，有時間、程序、PID、操作、路徑、結果和 Detail，**沒有呼叫堆疊欄位**。專案工作區遞迴搜尋及 Downloads、Desktop 目錄直接搜尋沒有找到 PML；不能排除其他位置存在 PML。先前畫面顯示擷取由虛擬記憶體支撐，且使用者當時另存 CSV；不能因此推斷不存在任何其他保存副本。現有 CSV 無法回答寫入目標值的呼叫堆疊、DLL 呼叫路徑或 32 次保存是否由同一函式完成；同一程序與相近時間只能證明事件關聯，不能替代堆疊。

本機 CSV 的確有 `ctfmon.exe` 查詢目標值，該組原生切換的第二次目標寫入後約 2.469 秒出現一次查詢；該時間點沒有與一筆已精確標記的注音組字輸出對齊，不能認定是即時生效的因果事件。原始日誌只保留本機，不上傳。

使用單一 IME-TCTIP provider 的短暫 `logman create trace` 權限探測，回傳 **Access is denied（5）**；工作階段未建立，後續查詢為不存在，沒有留下追蹤。此環境的非提升程序無法啟動該工作階段；依 [Microsoft ETW 控制工作階段文件](https://learn.microsoft.com/en-us/windows/win32/etw/controlling-event-tracing-sessions)，常見允許對象包括提升權限的管理員或已授權的 Performance Log Users。未變更使用者群組、ACL 或系統安全設定，也未繞過 UAC。

下一次若可透過正常 Windows UAC 授權，優先使用短時、容量上限、僅 IME-TCTIP 與必要的 TSF ALPC／OOPIME keyword 的受控追蹤，記錄 A／B 的單調時間及前景／焦點與實際注音輸出，分析時按程序及時間縮小。提供者可能是全系統範圍；即使只後處理特定 PID，原始 ETL 仍可能含其他程序或輸入資訊，必須保留私人本機、不上傳並於完成後正常停止工作階段。須先確認事件 schema 與追蹤權限；若不能定位輸出選項對應事件，不得宣稱已發現通知或 COM／IPC 機制。

本輪找到了可篩選的 Windows ETW 觀察目標及權限阻礙，**沒有找到已歸因的更新通知、可安全重現的 C# 候選或新的同步 A／B 實機輸出結果**。因此沒有建立候選原型或修改正式切換服務。這不代表專案停止，也不代表所有可行的系統介面不存在；保持 Draft、灰色未知及不發布正式版。

## 後續：正常 UAC 的 A／B 受控擷取

以正常 UAC 啟動限時、循環上限 16 MiB 的兩個獨立 ETW 工作階段，提供者均為 IME-TCTIP 與 TSF-msctf（選取 ALPC／OOPIME keyword）；沒有啟用全量 TCCORE、RPC 或 COMRuntime。提升程序與互動測試帳號的 SID 及 Session ID 經程式核對相同，正式 ZhuyinToggle 仍以一般程序啟動。原始 ETL、解碼 CSV、程序與焦點時間線均只保留私人本機。A、B 是**同一使用者／工作階段、不同時段的兩份擷取**，而非同一份追蹤或多次重複統計。兩份 ETL 均正常停止、解碼的 Events Lost 為 0；這不代表未啟用的事件不存在，也不排除其他資料收集限制。

| 組別 | 對齊證據 | 實際輸出 | 限制 |
|---|---|---|---|
| A 原生設定頁 | 使用者依指示繁→簡→繁；250 ms 前景採樣顯示設定視窗、其他視窗、記事本間切換。ETW 時間涵蓋操作；同 SID 觀察器在相關時間的 REG_SZ 樣本仍為 `0x00000000` | 使用者提供同一記事本截圖，依操作順序簡體「电脑中国」、繁體「電腦中國」各一行 | A 組沒有精確記錄實際字元提交時間或原生設定 RegSetValue；採樣可漏掉短暫值。本組無法證實目標寫入，亦不能解釋與先前 ProcMon 的差異。輸入法身分依使用者操作，未在本輪以 TSF profile 獨立驗證 |
| B ZhuyinToggle | 兩次 WM_HOTKEY 的 REG_SZ 即時回讀 1、0 均成功；記錄 UTC 02:59:02.861、02:59:09.319。採樣在兩次切換時均顯示同一記事本前景與同一輸入焦點 | 使用者提供截圖，兩次均為「電腦中國」；未觀察到簡體 | 採樣間隙可能有變化；截圖與程序日誌沒有逐字組字／提交時間，不能證明輸入法內部狀態或全部焦點行為 |

以 A 組可觀察的前景變更採樣時間為中心，±500 ms 有多組 TSF-msctf 事件，包含 ID 40/41 `ReceiveALPCMessages`、42/44 `ProcessALPCMessage`，發出程序有 `ctfmon.exe` 與 `explorer.exe`；例如 A 的兩次設定視窗前景變更附近各 43、45 筆。B 組兩次產品寫入即時回讀時間各 ±500 ms 的範圍，在本次已啟用的 TSF 資料中各為 0 筆。不同採樣／操作條件及單次 A/B 不支持以事件數作因果結論；A 同時有視窗切換，這些事件可能與焦點或其他活動相關。

整份 A 與 B 擷取的 TSF 事件 ID 集合同為 `{15,35,36,37,38,39,40,41,42,44}`；兩份解碼彙總均未見 IME-TCTIP 事件。尚未獨立確認 IME-TCTIP provider 實際啟用及是否會在目標路徑發事件，因此零事件不能作為該機制不存在的證明。事件 payload 未作可歸因的命令語意解析；事件名稱或接收 ALPC 本身不能證明它是設定更新通知。

先前第一次 ETW 權限成功的試擷取在產品按鍵前自動逾時，不能算入 A/B。**獨立的 C 組正常手動焦點對照 NOT TESTED**；A 組自然發生的視窗切換不能取代 C。沒有已證明的通知、COM／IPC 呼叫或可安全實作的 C# 更新候選，未改正式 `ImeModeService`；核心十次實際輸出及 Chrome 驗收仍未通過。測試後正式程序及 ETW 均結束，原始 `REG_SZ 0x00000000` 與自啟動停用狀態已確認。下一個證據關卡是釐清 A 組登錄值觀察不一致、核實 provider 啟用及其事件 schema，並在隱私與正常 UAC 前提下將設定寫入、實際字元提交與 ETW 時間標記在同一輪對齊；不得僅因 A 有 ALPC 便將其整合為切換機制。

## 無人值守：登錄環境與實際組字對照

在同一互動工作階段中，觀察器、SystemSettings、ctfmon、TextInputHost 與受限版的使用者 SID 和 Session ID 相符；檢查程序架構均為 x64。SystemSettings 與 TextInputHost 具有套件身分，但本次查得的 token 並非 AppContainer；這些資訊不足以證明或排除套件登錄重新導向。以下均僅限這次觀測環境。

以明確的 Registry32 和 Registry64 讀取同一 HKCU 路徑，兩者在基準皆為 REG_SZ `0x00000000`，受限版切換後皆為 `0x00000001`。因此產品寫入期間未觀察到兩個登錄檢視不一致；但本次沒有在原生設定頁輸出簡體的同時取得讀值，不能據此排除原生路徑的檢視或重新導向差異。

在可丟棄 TestHost 的本程序 TSF 設定檔檢查辨識 Microsoft Bopomofo、語言 0404 後，以實際注音鍵位輸入，觀察 IME_START、IME_RESULT、IME_END 和文字變更；繁體基準為「電腦中國」。保持宿主前景，透過預設快捷鍵觸發受限版，診斷顯示 REG_SZ 從 0 寫入 1 並回讀；隨後以注音鍵位再次組字，仍得到「電腦中國」，而非預期的「电脑中国」，可重現設定與輸出不同步。再次使用快捷鍵後回讀原值 0。這是一次受控宿主試驗，不代表記事本或 Chrome 的新測試，也不證明所有 TSF 組字狀態都可由 IMM 訊息觀察。

本次原生設定頁的輔助使用介面無法取得可用控制項狀態，沒有盲目操作選項，因此原生組的同步讀值與輸出、與其對照的 ETW 均為 NOT TESTED。先前原生組監測不一致的原因仍未釐清；尚須排查原生程序有效登錄位置、套件身分相關重新導向、採樣時序及其他設定或狀態更新，不應把任何一項視為已證實。沒有找到足以實作的通知或 C# 更新候選。未建立新 ETW 工作階段；本次測試程序已退出，登錄值回讀原始 REG_SZ `0x00000000`。正式功能與灰色未知圖示未變更。

## 既有 ProcMon 對照再核與登錄虛擬化範圍

唯讀重查既有 CSV（不是新的同步擷取）：目標設定的 `RegQueryValue`／`RegSetValue` 共 11 筆，匯出路徑均顯示為 `HKCU\Software\Microsoft\IME\15.0\IMETC\Enable Simplified Chinese Output`。其中 SystemSettings 先寫入 REG_SZ `0x00000001`，約 2.591 秒後寫回 `0x00000000`；這兩次之間 CSV 沒有列出 ctfmon 對該值的成功查詢，之後才列出讀取 0。這只能描述既有擷取中被列出的操作，不能證明 ctfmon 未以其他方式存取狀態、也不能將此擷取直接配對先前另一輪輸出或背景觀測。CSV 未包含呼叫堆疊，HKCU 顯示名稱本身也不足以確認每個程序的實際實體儲存位置。

本機唯讀檢查 Windows 設定套件清單：應用程式宣告的執行檔為 `SystemSettings.exe`，未找到名稱含 `Virtualization` 的宣告。這不構成此內建套件未虛擬化的證明。依 Microsoft 文件，[舊式 UAC registry virtualization](https://learn.microsoft.com/windows/win32/sysinfo/registry-virtualization) 適用範圍不包括本次 x64 程序的 HKCU 目標；但[套件化應用程式的 registry virtualization](https://learn.microsoft.com/en-us/windows/uwp/porting/desktop-to-uwp-behind-the-scenes) 是不同機制，文件所述行為只適用於虛擬化應用程式，不能僅依套件身分推定 SystemSettings 實際如何處理該鍵。原生頁與觀察器的實體位置是否相同仍未確認。

本次試圖透過現有桌面控制啟動原生頁時，應用程式存取授權逾時；沒有繞過授權或以其他自動化介面操作，未修改設定，沒有新的原生組字、通知或同步登錄證據。下一個有效關卡仍是恢復正常互動桌面控制後，在同一次原生切換中同時記錄選項、程序身分、可歸因登錄操作及實際輸出；如果需提升追蹤權限則遵循正常 UAC。未找到符合條件的 C# 候選，不修改產品或發布。

## 無人值守原生輸出與登錄對照（同一輪）

桌面控制這次可使用專案測試宿主；設定頁無法讀取輔助使用樹，依實際畫面選擇「微軟注音 → 常規 → 選擇輸入字元類型」，而非建立產品 UI 自動化方案。基準原生頁顯示繁體，HKCU 目標 REG_SZ 回讀 `0x00000000`。專用可丟棄宿主先以實際注音鍵位輸出「電腦中國」，宿主記錄 IME_START／IME_RESULT／IME_END，且以自身 TSF 設定檔檢查回報 Microsoft Bopomofo 與輸入已結束。

原生頁切換到簡體並目視確認後，透過同一使用者的一般程序明確讀取 Registry32 和 Registry64，兩者仍回報 REG_SZ `0x00000000`。之後回到同一宿主，以實際注音鍵位產生「电脑中国」，記錄新的 IME_START／RESULT／END 與文字變更；再次讀取目標值仍為 `0x00000000`。原生頁還原繁體後，宿主再實際組字得到「電腦中國」，組字事件完成且設定檔檢查通過。這是一次繁→簡→繁控制組；操作原生頁與返回宿主必然發生正常視窗切換，因此不是持續前景或無感切換的證據。

本輪在原生頁顯示簡體的期間讀到 0，並在其後觀察簡體實際輸出，比先前依賴使用者截圖的證據更直接；但登錄讀取是離散抽樣，不是連續 trace，不能排除極短暫的變更及覆寫，也不能確認 SystemSettings 實際儲存位置。未追蹤到寫入事件、未識別通知、未證實虛擬化，不能聲稱找到根因或可安全重現的 API。這個觀察亦不應與先前不同時間的 ProcMon 擷取直接視為同一次事件。

測試後原生頁已設回繁體且實際繁體輸出確認；宿主與本輪開啟的設定視窗已關閉。本輪未啟動 ETW 或額外提升權限的追蹤程序，未修改正式產品；產品快捷鍵即時輸出、記事本十次往返及 Chrome 仍未通過驗收。後續需要一份具適當權限與隱私界限的同輪 registry 事件及目標程序位置觀測，對齊原生頁選擇與宿主 IME 時間，之後才可判斷通知或其他候選。

## 同輪 Kernel Registry ETW 與實際注音輸出

透過正常 UAC 啟動本機短時 Kernel Registry ETW，僅啟用 `SetValueKey` keyword、循環檔案上限 16 MiB；提升程序的 SID 與互動工作階段經核對與測試使用者相同。擷取約 88 秒後正常停止；解碼摘要為 499 筆 SetValueKey 事件、Events Lost 0。原始 ETL 與完整解碼只保留本機私人目錄。Events Lost 為 0 不代表未啟用的事件或未收集的 IPC 不存在。

同一輪專用宿主以實際注音鍵位完成「電腦中國」→「电脑中国」→「電腦中國」，各組有新的 IME_START、IME_RESULT、IME_END、文字變更，並回報自身 TSF Microsoft Bopomofo 設定檔及組字已結束。原生設定頁先選簡體再恢復繁體；使用設定頁期間有正常的前景視窗切換，不能據此宣稱無焦點變化或正式產品通過驗收。

在同一份 ETW 中找到兩筆事件名稱 `Enable Simplified Chinese Output`，均屬 Kernel Registry Event ID 5 `SetValueKey`，程序 PID 在擷取後以系統程序清單核對為 `SystemSettings.exe`、同一互動工作階段；事件時間分別為 UTC 12:37:16.758 與 12:37:44.120，兩筆皆發生在相應簡體、繁體組字提交之前。該事件解碼顯示型別 1、資料長度 22，但本次未解出寫入字串內容；KeyName 欄位為空，不能從此 ETW 證明實體機碼路徑或字串值。早先不同輪 ProcMon 曾記錄目標路徑與 0／1，不應混作本輪已觀察事實。QPC 與 UTC 以擷取啟動時的時鐘配對做近似對照，存在取樣延遲，不能視為精準因果計時。

這次同輪證明原生操作期間發生具程序歸因的同名登錄寫入事件及繁簡實際輸出變化，但未找到通知或公開可重現介面；不能推論同名寫入即為更新原因。`SetValueKey` keyword 未涵蓋其他事件，不能排除查詢、COM、IPC、快取或其他程序行為；亦不能解決背景觀察器值不同的實體位置問題。未盲目複寫其他鍵、廣播訊息或實作缺乏支持的候選。測試結束後原生頁與實際輸出恢復繁體，背景 REG_SZ 回讀 `0x00000000`，追蹤及專用視窗已停止；正式產品和灰色未知狀態未修改。

## KeyObject 關聯與原生同輪補充追蹤

先重新檢查前次只啟用 SetValueKey 的 ETL：兩筆目標同名寫入各自的 KeyObject 在解碼資料中均只出現一次，沒有同物件的開啟／建立事件可還原路徑。

本輪正常 UAC 啟動官方 ProcMon 原生 PML 擷取；全系統資料在約 4 秒超過預設 128 MiB 停止門檻（實際檔案約 141.6 MB，因檢查間隔可能超過上限），自動停止並確認程序退出。此時尚未執行目標切換，所以該 PML **不能**用作本輪切換證據。原始 PML 留在本機私人目錄。

改以正常 UAC 啟用限時、16 MiB 循環 ETW，包含 Kernel Registry `CreateKey`、`OpenKey`、`SetValueKey`。專用宿主的實際微軟注音輸出依序為「電腦中國」→「电脑中国」→「電腦中國」，具有 IME_START／RESULT／END 與自身 TSF 設定檔檢查；簡體期間背景觀察器讀得 REG_SZ `0x00000000`。結束後原生頁與實際輸出恢復繁體，設定值回讀 `0x00000000`。

循環 ETL 達到 16 MiB，停止並解碼後列出 63,187 筆事件、Events Lost 0；**循環覆寫不同於 Events Lost**，前段資料可能已被取代。解碼後只找到一筆目標同名 SetValueKey，其 KeyObject 可與同 PID、約 0.116 毫秒前的 CreateKey 結果物件關聯；後者顯示相對路徑 `Software\Microsoft\IME\15.0\IMETC`。但該 CreateKey 的根 KeyObject 在保留的同 PID OpenKey／CreateKey 中找不到建立對應，因此仍無法還原完整實體根路徑，不能證明背景觀察器和原生頁使用同一位置。擷取後程序已退出，未保留同輪可靠的 PID→程序映射，此筆 ETW PID 不應單獨宣稱已驗證為 SystemSettings。該事件沒有解出寫入資料；首個方向的同名事件未在循環檔保留，不能作雙向寫入證據。

未取得完整 PML 切換事件、完整機碼路徑／寫入值或成功原生與產品失敗的同條件完整對照；因此不推定套件虛擬化、不建立缺乏證據的候選或修改正式產品。下一步需要在受控隱私界限下預設 ProcMon 過濾及更短擷取窗，或使用具可歸因 PID 映射與足夠容量的登錄追蹤，避免全系統高頻 OpenKey 覆寫必要的根機碼事件。
